# CUDA Profiler Details: Per-Kernel Information & CPU-GPU Call Traces

> What information does the PyTorch profiler capture per CUDA kernel, and what CPU-GPU call traces are recorded?

## Source of Truth

- **Tracing backend**: CUPTI (CUDA Profiling Tools Interface)
- **Trace analyzed**: Generated by running an MLP model on Tesla T4, CUDA 12.08, CUPTI v26
- **Profiler library**: [Kineto](https://github.com/pytorch/kineto) (PyTorch's profiling backend)
- **CUPTI docs**: https://docs.nvidia.com/cupti/

---

## 3. Per-Kernel Information from CUPTI (Source: Kineto/CuptiActivity.h)

The underlying Kineto library captures these fields from CUPTI:

### Compute Kernel Activity (`CUpti_ActivityKernel4`):
- `name` -- Kernel function name
- `deviceId` -- GPU device
- `contextId` -- CUDA context
- `streamId` -- CUDA stream
- `correlationId` -- Links to runtime API call
- `start` / `end` -- Timestamps (nanoseconds)
- `gridX`, `gridY`, `gridZ` -- Grid dimensions
- `blockX`, `blockY`, `blockZ` -- Block dimensions
- `staticSharedMemory` -- Static shared memory (bytes)
- `dynamicSharedMemory` -- Dynamic shared memory (bytes)
- `registersPerThread` -- Register count per thread
- `localMemoryTotal` -- Total local memory per thread
- `localMemoryPerThread` -- Local memory used per thread
- `queued` -- Queued timestamp
- `submitted` -- Submitted to GPU timestamp
- `completed` -- Completion timestamp
- `launchType` -- Regular, cooperative, etc.

### Occupancy Calculation (computed by Kineto):
- `blocksPerSm` = gridX*gridY*gridZ / numSms
- `warpsPerSm` = blocksPerSm * (blockX*blockY*blockZ / warpSize)
- `kernelOccupancy` = estimated achieved occupancy using CUPTI occupancy API

Each CUDA runtime call captures:

| Field | Description |

| `cbid` | CUPTI callback ID |

### Runtime APIs observed in trace:
- `cudaLaunchKernel` -- Kernel launch
- `cudaMalloc` / `cudaFree` -- Memory allocation
- `cudaDeviceSynchronize` -- Synchronization
- `cudaDeviceGetAttribute` -- Device queries
- `cudaGetDriverEntryPoint` -- Driver entry point lookup
- `cudaGetSymbolAddress` -- Symbol address lookup
- `cudaStreamIsCapturing` -- CUDA Graph capture check
- `cudaOccupancyMaxActiveBlocksPerMultiprocessor` -- Occupancy query

## 6. CPU-GPU Call Trace Structure

The PyTorch profiler captures a **hierarchical tree** of events from the CPU side down to GPU kernel execution:

```
User Annotation (record_function)
  -> PyTorch High-Level Op (e.g., aten::linear)
    -> Decomposed Ops (e.g., aten::t, aten::transpose, aten::addmm)
      -> CUDA Runtime API Calls (e.g., cudaLaunchKernel)
        -> [Flow Event: ac2g]
          -> GPU Kernel Execution (e.g., volta_sgemm_32x32_sliced1x4_tn)
```

### CPU-Side Event Categories

**User Annotations** (`cat: "user_annotation"`):
Created by `torch.profiler.record_function("name")` context manager or decorator.

**CPU Operators** (`cat: "cpu_op"`):
Every ATen operator call is recorded with full input metadata:

- **High-level operators** (composite): `aten::linear`, `aten::conv2d`, `aten::batch_norm`, `aten::embedding`
- **Decomposed operators**: `aten::t`, `aten::transpose`, `aten::permute`, `aten::as_strided`, `aten::addmm`, `aten::mm`, `aten::_to_copy`
- **Memory operators**: `aten::empty_strided`, `aten::detach`, `aten::set_`
- **Autograd operators** (backward pass): `autograd::engine::evaluate_function`

### GPU-Side Event Categories

- **GPU Kernels** (`cat: "kernel"`): Actual compute executed on GPU hardware
- **GPU User Annotations** (`cat: "gpu_user_annotation"`): Mirror of CPU-side annotations projected onto GPU timeline
- **GPU Memory Operations**: `cat: "gpu_memcpy"` (HtoD, DtoH, DtoD copies), `cat: "gpu_memset"` (memory fill)

## 7. Correlation / Flow Events (`cat: "ac2g"`)

"API-Call-to-GPU" flow events link CPU runtime calls to GPU activities:

```json
// Flow start (on CPU side, at cudaLaunchKernel)
{"ph": "s", "id": 1156, "cat": "ac2g", "name": "ac2g"}

// Flow end (on GPU side, at kernel start)
{"ph": "f", "id": 1156, "cat": "ac2g", "name": "ac2g", "bp": "e"}
```

The correlation chain:
1. **CPU op** has `External id: N`
2. **CUDA runtime call** has `External id: N` (same parent) + `correlation: M`
3. **Flow event** uses `id: M` to link CPU->GPU
4. **GPU kernel** has `correlation: M` and `External id: N`

## 8. Complete Call Trace Example

```
[model_inference]  (user_annotation, 141.6ms)
  |
  +-- aten::linear  (cpu_op, 137.4ms)
  |     |
  |     +-- aten::t  (cpu_op, 9.6ms)
  |     |     +-- aten::transpose  (cpu_op, 3.4ms)
  |     |           +-- aten::as_strided  (cpu_op, 1.8ms)
  |     |
  |     +-- aten::addmm  (cpu_op, 123.6ms)
  |           |
  |           +-- [memory] alloc 1536 bytes
  |           +-- [memory] alloc 8519680 bytes
  |           +-- [memory] alloc 1048576 bytes
  |           |
  |           +-- cudaMalloc (cuda_runtime)
  |           +-- cudaDeviceGetAttribute x16 (cuda_runtime)
  |           +-- cudaLaunchKernel (cuda_runtime, correlation: 1156)
  |                 |
  |                 +-- [ac2g flow: 1156]
  |                       |
  |                       +-- volta_sgemm_32x32_sliced1x4_tn (kernel, 16.0us)
  |
  +-- [memory] free -1536 bytes
```

## 10. Additional Profiler Options

### With `with_stack=True`:
Each event additionally captures Python source location:
```python
# Example from key_averages().table(sort_by="cuda_time_total", row_limit=10)
# Name    | Source Location
# addmm   | .../torch/nn/functional.py(1848): linear
#         | .../model.py(25): forward
```

### With `with_flops=True`:
FLOPS estimates for supported ops (matmul, conv2d, BMM):
```
aten::addmm  | 81920 FLOPS  (M=32, K=128, N=10 -> 2*M*K*N)
```

### With `with_modules=True`:
Module hierarchy for TorchScript models:
```
nn.Module: Linear | aten::addmm
```

### With `profile_memory=True`:
Memory allocation tracking per operator with `device_memory_usage` and `self_device_memory_usage` fields.

## 11. Additional Event Categories

| Category | Description |
|---|---|
| `user_annotation` | User-defined regions via `record_function()` |
| `gpu_user_annotation` | GPU-side mirror of user annotations |
| `overhead` | CUPTI overhead (buffer requests, module loading) |
| `Trace` | Profiler metadata span |
| Metadata (`ph: "M"`) | Process/thread naming and sort order |

### Profiler Overhead Events (`cat: "overhead"`)

| Event | Description |
|---|---|
| `Activity Buffer Request` | Time spent requesting CUPTI activity buffers |
| `Runtime Triggered Module Loading` | Module loading triggered by runtime calls |
| `Lazy Function Loading` | Lazy loading of function metadata |

### Metadata Events (`ph: "M"`)

| Event | Purpose |
|---|---|
| `process_name` | Names processes (e.g., "python3") |
| `process_labels` | Labels (e.g., "CPU", "GPU 0") |
| `process_sort_index` | Sort order in trace viewer |
| `thread_name` | Names threads (e.g., "stream 7", "thread 426") |
| `thread_sort_index` | Thread sort order |
| `Iteration Start` | Marks profiler step boundaries |
| `Record Window End` | Marks end of profiling window |
